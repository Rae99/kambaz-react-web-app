第一个useEffect

useEffect(() => {
  if (!isNewQuiz && !quiz) {
    navigate(`/Kambaz/Courses/${cid}/Quizzes`);
    return;
  }
}, [quiz, isNewQuiz, cid, navigate]);

	目的：当这是“编辑已有 quiz”的场景（!isNewQuiz），但本地 store 里找不到该 quiz 对象（!quiz）时，把你导航回列表，避免编辑一个不存在/已被删除的 quiz。
	•	问题点：刷新时 Redux 内存为空，quiz 会先是 undefined。如果你没有先去后端拉取该 quiz，这个 effect 会立刻触发，把你从 /edit 踢回去。这就是你遇到“刷新 /edit 被踢走”的根因。

结论：这个 effect 适合在**确认后端也没有（404）**时才跳转，而不是在“本地还没加载到”的时候就跳。


第二个useEffect

useEffect(() => {
  if (quiz && quizForm.questions.length === 0) {
    setQuizForm({ ...用 quiz 覆盖一整份表单... });
  }
}, [quiz, quizForm.questions.length]);
  
我看了你这段逻辑，其实 if (quiz && quizForm.questions.length === 0) 这个条件的本意大概率是为了做一次性的“首加载填充”，避免覆盖用户已经改过的内容。

它想表达的思路是：
	•	当我第一次进入编辑页面时，如果这是个已有 quiz（quiz 有值），而且我当前本地表单 quizForm 里的题目列表是空的（questions.length === 0），那就说明这是刚初始化的表单，还没被用户填过。
	•	那就用从 Redux / 后端拿到的 quiz 数据把整个 quizForm 覆盖一次，填满表单字段。

这类判断有点像 “hydrate only once” 的替代写法。

为什么它听起来很 buggy

你说得没错，用 “questions.length === 0” 当成“是否是第一次加载”的标志非常脆弱：
	•	如果用户手动把题目删光了（变成 0 个），它会错误地认为是第一次加载，然后用旧的 quiz 数据把所有字段又覆盖一遍，等于撤销了用户刚做的修改。
	•	如果是新建 quiz（isNewQuiz），初始状态本来就是 0 个题，但这时 quiz 是 null，不会触发这个分支，所以不会出 bug。但编辑场景下就有风险。

•	这个“只要长度是 0 就 hydrate”的写法是个隐式的“一次性”判断，容易在边界场景误触发。

结论：hydrate 应该基于“是否已经 hydrate 过”来判定（例如用 hasHydrated 或 isDirty 标记），而不是用 questions.length === 0 这种易误判的条件。




你的数据流（按当前代码）

新建（qid === 'new'）
	1.	quiz 为 null，初始 quizForm 用默认值（New Quiz 等）渲染。
	2.	用户编辑时，通过 handleFormChange 只改本地 quizForm。
	3.	点击 Save：
	•	走 handleSave(true) → 序列化日期 →
coursesClient.createQuizForCourse → dispatch(addQuiz(newQuiz)) → navigate 回列表。

编辑已有（qid !== 'new'，从**列表点“Edit”**进入）
	1.	如果 Redux 里已经有该 quiz：
	•	第一个 effect 不跳（quiz 存在）。
	•	第二个 effect 触发一次（因为 quiz 存在且表单初始问题数为 0），用 quiz 覆盖 quizForm，表单填满。
	2.	用户编辑 → 只改本地 quizForm。
	3.	点击 Save：
	•	quizzesClient.updateQuiz → dispatch(updateQuiz(updatedQuiz)) → navigate 回列表。

刷新 /edit（问题最多的场景）
	1.	刷新后 Redux 清空，quiz 是 undefined。
	2.	第一个 effect 看到 !quiz，立刻 navigate 回列表 → 你就被踢走了。
	3.	第二个 effect不会触发，因为 quiz 不存在。
